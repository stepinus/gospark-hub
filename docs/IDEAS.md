# Идеи этапа 2 (за пределами паритета)

Сюда пишем идеи, чтобы не потерять. Источник — владелец хаба, заметки по ходу порта.

В этап 2 входят: перепись `sah` на Go, интеграция с llama-swap и идеи ниже.
Десктоп (Wails/Fyne), RTX Spark и Strix Halo — этап 3, см. `docs/PLAN.md`.

## Spark Doctor UI — страница тюнинга системы

Референс: <https://github.com/joeynyc/spark-doctor> (MIT, Python 3.11+, CLI, read-only).

Что делает апстрим: собирает систему, GPU, память, docker, runtime, сеть, рецепты;
прогоняет правила DGX Spark и печатает короткий ответ «что не так, почему, что делать».
Ключевые правила, которые нам интересны: низкое потребление под нагрузкой, риск
термотроттлинга/выключения, давление UMA и swap, неготовый NVIDIA container runtime,
две тяжёлые модели одновременно, vLLM KV-cache OOM, Xid-ошибки, NIC ниже 1 Гбит/с,
валидатор рецепта (TP vs число GPU, arm64, бюджет памяти, gou_memory_utilization).

Идея для хаба: страница `/doctor` —
- запускает `spark-doctor scan --json` (или повторяет его коллекторы на Go),
- показывает находки списком: правило, severity, evidence, следующий шаг,
- тюнинг-подсказки рядом с параметрами запуска (KV cache, gpu_memory_utilization, TTL),
- результат кэшируется (scan по кнопке + по cron), история находок в SQLite,
- автофиксов нет — только инструкции, как в апстриме (это осознанное свойство, не недоработка).

Открытые вопросы: брать CLI как внешнюю зависимость (питон в образе) или переписать
коллекторы на Go; нужен ли live-режим (SSE по метрикам) или достаточно on-demand scan.

## Интерактивный редактор конфига spark-swap

К интеграции с llama-swap: визуальный редактор конфига со шкалами заполнения памяти.
Источник данных — рецепты моделей (params_b, квантование, kv_cache_bytes, контекст);
шкала показывает, сколько unified-памяти съест модель и остаётся ли на вторую.
После первого запуска рецепта перезаписывать оценку фактическими данными с машины
(занятая память процесса, реальный размер KV, замеренный пик) — то есть «ожидаемое
из рецепта → фактическое после прогона», с сохранением обоих значений.

## Страница запуска бенчмарков

Запуск бенчмарков из UI: выбор модели/рецепта, прогон, визуализация процесса
(прогресс по задачам, скорость, токены, температура/память), сохранение результата
с привязкой к модели и параметрам запуска. Нужна история: одна модель в разных
рецептах — сравнимые строки, как в `~/Workspace/llm-inference-bench`.

## Реестр сопроводительных сервисов

Страница установки «окружения вокруг моделей»: локальные системы памяти (OpenViking,
Enzyme и прочие), AI-агенты, кравлеры, веб-поиск, очереди. Для каждого — что это,
какие порты/тома/ключи нужны, статус (нет / установлен / запущен / упал),
установка и удаление из UI, health-проверка. По сути каталог companion-сервисов
рядом с каталогом моделей.

## Редактор рецептов и работа с регистрами

Страница редактирования рецепта + управление регистрами (добавить регистр, обновить).
Правка рецепта = **копия**: оригинал не трогаем, создаём отредактированную копию,
чтобы обновление регистров из апстрима не давало конфликтов. Копия помечается как
локальная (происхождение: регистр + исходный slug + хеш/дата оригинала), чтобы при
обновлении видеть «оригинал изменился, твоя копия — от старой версии».
Кнопка «обновить/подтянуть новые рецепты» — перечитывает регистры и раскладывает
новое/обновлённое без рестарта демона (watch по mtime уже есть в фазе 2, тут нужен
триггер из UI + отчёт «что приехало»).

## Переключение Docker / Podman в настройках

Режим работы контейнеров: docker или podman. У podman совместимый CLI, поэтому при
запуске рецептур достаточно подменять `docker` → `podman` (флаг/алиас в настройках,
прокидывается в команды запуска и в проверки runtime). Требует честной проверки:
`podman` без `podman-docker`-сима не знает `docker compose`, и путь сокета другой —
настройка должна валидировать окружение при переключении, а не падать на первом запуске.

## Общий кеш медиамоделей (только не-LLM)

Сейчас обычные LLM-модели запаяны в контейнеры — так и оставляем, их не шарим.
А медиамодели (аудио/видео, MiniMax и т.п.) дублировать нет смысла: один и тот же
файл нужен и ComfyUI-воркфлоу, и отдельному интерфейсу вроде MiniMax Music Studio.

Договорённость:
- общий каталог медиамоделей на хосте, как сейчас у ComfyUI
  (`/media/nvidia/HDD_ENOT/comfyui-models` + симлинк в `data/models`) — сервисы
  монтируют его себе (bind-mount для контейнеров) и ссылаются на файлы, а не копируют;
- в каталоге моделей хаба — отдельная вкладка «медиа», отдельно от LLM-рецептов;
- никакого учёта потребителей и refcount: синхронизировать это дороже, чем польза.
  Потребители определяются по факту (маунты/конфиги), удаление — вручную.
